# A. 설계 선택 실험 (합성 데이터)

## 1. 회전 augmentation 범위

- **질문**: 천장 카메라는 방향성이 없으니 360° 회전이 맞는가?
- **가설**: 카메라와 선반이 고정이면 접근 방향이 제한되므로 무제한 회전은 신호를 지움

```bash
.venv/bin/python -m car.train.train_action --store data/processed/demo_skeletons.npz \
  --model stgcn --set train.epochs=40 train.aug_rotation_deg=30
```

| 조건 | Accuracy | Macro F1 | Best epoch |
|---|---|---|---|
| 증강 없음 | 0.730 | 0.721 | 16 |
| **회전 ±30°** | **0.839** | **0.835** | 31 |
| 회전 ±180° | 0.784 | 0.776 | — |

- 증강 없음: 16 epoch에 과적합 시작
- ±180°: "팔이 선반 쪽으로 뻗었다"는 방향 정보 소실
- **채택**: `train.aug_rotation_deg: 30`

## 2. Skeleton 정규화 방식

| 방식 | 처리 | Accuracy | Macro F1 |
|---|---|---|---|
| **`torso`** | 엉덩이 중점 이동, 몸통/어깨 최대값으로 나눔 | **0.849** | **0.847** |
| `bbox` | 박스 원점 기준, 박스 크기로 나눔 | 0.831 | 0.831 |
| `none` | 프레임 크기로만 나눔 | 0.644 | 0.640 |

- 정규화 없으면 프레임 내 위치에 따라 입력이 달라져 0.644로 급락
- `bbox`는 박스 검출 품질에 연동되어 불안정
- **채택**: `sequence.normalize: torso`
- 부가 이점: 카메라 높이가 바뀌어도 동일 입력 → 타 매장 배포 시 재학습 부담 감소

## 3. 윈도우 라벨 결정 방식

- **질문**: 30프레임 윈도우가 두 행동에 걸칠 때 어느 라벨을 쓰는가?

| 방식 | Accuracy | 학습/검증 윈도우 |
|---|---|---|
| **`last`** | **0.839** | 935 / 385 |
| `majority` | 0.953 | 935 / 385 |
| `drop_mixed` | 1.000 | 263 / 110 |

- **숫자가 높은 쪽을 고르면 안 되는 사례**
- `drop_mixed` 1.000: 전이 구간을 버려 학습 데이터가 1,320 → 373으로 감소, 문제 자체가 쉬워짐
- `majority`: 학습은 쉬우나 실시간 추론 조건("지금 무엇을 하는가")과 불일치
- **채택**: `last` — 세 방식 중 가장 낮지만 실배포를 정직하게 반영

## 4. ST-GCN grouped convolution 그룹 수

- 논문 파라미터 922,301개에서 역산 (학습 불필요, 구조만으로 계산)

| groups | 파라미터 | 논문 대비 |
|---|---|---|
| 1 | 1,983,021 | +115% |
| **2** | **1,018,413** | **+10.4%** |
| 4 | 535,725 | -41.9% |
| 8 | 294,573 | -68.1% |

- 정확히 맞지 않는 이유: 논문이 시간축 커널 크기 미기재
- `temporal_kernel=7`이면 846,381개로 논문보다 작아짐
- **채택**: `stgcn.groups: 2`
- LSTM은 `dense_hidden=32`에서 353,549개 → 논문(352,775) 대비 +0.2%

## 5. 추적기 appearance descriptor

| descriptor | 추적 지연 | 추가 모델 | 적합 상황 |
|---|---|---|---|
| `none` | 최저 | 없음 | 1인 촬영 |
| **`histogram`** | 낮음 | 없음 | 옷 색 다른 소수 인원 |
| `reid` | 높음 | ReID 망 | 혼잡, 옷 색 유사 |

- **채택**: `tracker.appearance: histogram`
- **버그 발견**: appearance 없을 때 matching cascade를 건너뛰면 미검출 트랙이 영구 복구 불가
  - 단위 테스트 `test_track_id_survives_a_gap_shorter_than_max_age`가 검출
  - cascade가 motion-only 비용으로도 동작하도록 수정

# B. 실데이터 결과 (MERL Shopping)

- 데이터 출처: `https://www.merl.com/pub/tmarks/MERL_Shopping_Dataset/`
- 규모: 영상 106개 (1.8 GB) + 라벨 106개

## 6. 트랙 연속성 문제

- **증상**: 91,168 프레임에서 윈도우가 8,279개만 생성

| 지표 | 값 |
|---|---|
| 트랙 연속 구간 수 | 5,258 |
| 30프레임 이상 구간 | 732 |
| 구간 길이 중앙값 | 5 프레임 |
| 사용 가능 프레임 | 61,173 / 91,168 |

- **원인**: 고객이 선반 앞에서 몸을 숙이면 검출 실패 → 추적기가 새 ID 부여 → 시퀀스 절단
- **대응 1**: 클립당 단일 트랙 병합 (`keep_primary_track`)
  - MERL은 1인 촬영이므로 2번째 트랙은 검출 오류 또는 재획득
- **대응 2**: 프레임 간격 허용치 확대 (`sequence.max_gap` 6 → 12)
  - 10 fps에서 간격 12는 원본 0.4초, 연속 3프레임 미검출까지 허용

| 설정 | 윈도우 수 |
|---|---|
| 원본 | 8,279 |
| 단일 트랙 병합 | 9,299 |
| 병합 + max_gap=12 | **10,979** |

## 7. 기존 pose 기반 행동 인식

- 클립 단위 분할, 150 epoch, 조기 종료, `balance_ratio=1.5`

| Metric | ST-GCN | LSTM | 논문 ST-GCN | 논문 LSTM |
|---|---|---|---|---|
| Accuracy | 0.574 | 0.602 | 0.93 | 0.85 |
| Mean F1 | 0.56 | 0.59 | 0.90 | 0.82 |

- 혼동 패턴은 논문과 동일 방향
  - "Retract From Shelf" → "Hand In Shelf" 오인이 최다 (394개 중 123개)
  - 논문 서술: "Reach to Shelf와 Retract From Shelf 사이에서 오차가 많이 발생"

## 8. 분할 단위 검증

- 동일 데이터·모델·하이퍼파라미터, **분할 단위만** 변경

| 분할 단위 | Accuracy | 데이터 누수 |
|---|---|---|
| 윈도우 단위 (무작위) | **0.70** | 인접 윈도우 25프레임 공유 |
| 클립 단위 | **0.57** | 없음 |

- **13%p 차이**
- 30프레임 윈도우를 stride 5로 생성 → 인접 윈도우가 25프레임 중복
- 논문은 "70%/30%"만 명시하고 단위 미기재
- 표 4.3이 클래스별 **프레임 수**를 제시 → 프레임 단위 분할 가능성 (윈도우보다 누수 큼)
- 윈도우 단위 0.70으로도 논문 0.93은 설명되지 않음 → 자세추정 품질 의심 (§9)

## 9. Custom YOLOv11n-Pose

**추출 단계**

**논문 표 4.4 최종 대조**

| Metric | ST-GCN | LSTM | 논문 ST-GCN | 논문 LSTM |
|---|---|---|---|---|
| Accuracy | 0.70 | 0.69 | 0.93 | 0.85 |
| Macro precision | 0.69 | 0.68 | 0.90 | 0.83 |
| Macro recall | 0.69 | 0.68 | 0.85 | 0.83 |
| Mean F1 | 0.69 | 0.68 | 0.90 | 0.82 |
| Parameters | 1,018,413 | 353,549 | 922,301 | 352,775 |
| 학습 시간 | 3,147초 | 283초 | — | — |

**클래스별 성능 (ST-GCN)**

| 클래스 | Precision | Recall | F1 |
|---|---|---|---|
| Reach To Shelf | 0.71 | 0.63 | 0.67 |
| Retract From Shelf | 0.64 | 0.68 | 0.66 |
| Hand In Shelf | 0.58 | 0.70 | 0.63 |
| Inspect Product | 0.71 | 0.69 | 0.70 |
| Inspect Shelf | **0.79** | **0.76** | **0.77** |

**핵심 해석**

- 성능 향상의 주 요인은 관절 정확도가 아니라 **검출 연속성**
- 행동 인식은 30프레임 연속 시퀀스 필요 → 중간 1회 검출 실패로 시퀀스 전체 무효
- 유효 시퀀스 3.1배 증가가 12.7%p 향상의 주된 경로

**차이 요인 정리**

| 요인 | 기여 | 확인 방법 |
|---|---|---|
| Custom pose 학습 | +12.7%p | 두 store로 각각 학습 |
| 분할 단위 (클립 → 윈도우) | +12.7%p | 동일 데이터, 분할만 변경 |
| 트랙 연속성 개선 | 윈도우 3배 | §6 |

- 두 요인 합산 시 0.83 근처 예상되나 데이터 누수 수용 수치
- 클립 단위 0.70이 신규 매장 배포 시 기대값에 근접

**ST-GCN vs LSTM**

- 정확도 차이 0.7%p로 미미 (논문은 8%p 우위 보고)
- 파라미터 2.9배, 학습 시간 11배, 추론 지연 2.5배 차이
- **온디바이스에서는 LSTM이 합리적** (논문과 동일 결론)

## 11. 추적 성능 (논문 표 2.2)

- 평가 대상: 공식 테스트 피험자 12개 클립, 17,445 프레임

- **논문의 +6%p 향상 미재현**
- 원인 추정

# C. 런타임 성능

## 12. 모델 및 파이프라인 속도

**행동 모델 단독**

| 모델 | 파라미터 | 지연 | 처리율 |
|---|---|---|---|
| ST-GCN | 1,018,413 | 8.70 ms | 115 Hz |
| LSTM | 353,549 | 3.49 ms | 286 Hz |

**자세추정 단독** (640 px, 4인 프레임, 15회 평균)

| 백엔드 | 지연 | fps |
|---|---|---|
| PyTorch FP32 | 101 ms | 9.9 |
| PyTorch FP16 | 89 ms | 11.2 |
| TensorRT FP16 | 45 ms | 22.3 |
| Custom pose FP32 | 40 ms | 24.8 |

- **자세추정이 전체 지연의 90% 이상을 차지하는 병목**

**전체 파이프라인** (920×680 MERL 영상)

| 구성 | fps | 자세추정 | 추적 | 행동분류 |
|---|---|---|---|---|
| Custom pose + LSTM | **23.9** | 38.8 ms | 0.8 ms | 0.9 ms |
| Custom pose + ST-GCN | 22.7 | 39.2 ms | 0.8 ms | 2.7 ms |
| 기존 pose + ST-GCN (TensorRT) | 18.6 | 24.5 ms | 3.7 ms | 15.1 ms |

**논문 표 4.5 대조**

| 항목 | 논문 (AGX Xavier 32GB) | 본 구현 (Orin NX 16GB, 25W) |
|---|---|---|
| Pose + LSTM fps | 32 | 23.9 |
| Pose + ST-GCN fps | 28 | 22.7 |
| 프로세스 메모리 | 5.8–7.2 GB / 32 GB | 1.3–1.5 GB / 16 GB |

- LSTM이 ST-GCN보다 빠르다는 **경향은 재현**
- 절대값 직접 비교 불가 (보드 상이, 전력 모드 25W 제한)
- Jetson은 GPU·CPU 메모리 공유 → `cuda.mem_get_info()`는 시스템 전체값이므로 프로세스 RSS를 비교 기준으로 사용

## 13. int8 양자화

- 논문: float32 → int8 TFLite
- 본 구현: PyTorch dynamic int8 (Jetson은 TensorRT가 더 적합)

| 모델 | 정밀도 | Accuracy | 모델 크기 | CPU 지연 |
|---|---|---|---|---|
| LSTM | fp32 | 0.746 | 1.42 MB | 36.0 ms |
| LSTM | int8 | 0.748 | **0.39 MB** | 73.6 ms |
| ST-GCN | fp32 | 0.757 | 4.13 MB | 376 ms |
| ST-GCN | int8 | 0.757 | 4.13 MB | 402 ms |

- LSTM: 크기 **73% 감소**, 정확도 유지
- LSTM: CPU 지연 **2배 증가** (ARM qnnpack 백엔드 미최적화)
- ST-GCN: 효과 없음 (dynamic 양자화는 Linear/LSTM만 대상, ST-GCN은 Conv2d 기반)
- 실제 배포는 GPU 경로 → CPU int8의 실익 제한적
- **교훈**: 양자화 효과는 목표 하드웨어에서 직접 검증 필요
